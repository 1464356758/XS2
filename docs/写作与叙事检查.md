# V4.3 写作任务书与叙事检查

本规则用于新书。唯一入口仍是一个GPT，工具不调用模型、不自动审稿、不增加作者转发步骤。使用新初始化包的bootstrap默认启用`narrative_review_required=true`；旧书没有该配置时保持原检查，不能把升级代码说成旧章已经补审。

冻结、真实发布回执、三轮返修、到期全文回看及事实来源规则继续有效。新增内容只在既有发布前报告中集中交付，不另建一组评分员。

## 一、三个资料视角

|资料|内容|用途与限制|
|---|---|---|
|author，默认|设定、路线、当前状态、上章、近五章推进、相关记忆和开放项|规划与一致性核对。超预算时分批真实读取来源，不能静默截断|
|writer|已登记的自然语言任务书、必要硬边界、读者体验、场景预算、上章正文|起草。没有原始JSON状态、检查编号或远期大纲；约束是否提取完整仍须GPT核对|
|reader|当前候选、最近三章正文；更早章节优先用带证据的非空读者回顾，回顾为空或缺失时使用原文|诊断理解和阅读体验。不注入canon、roadmap、原始章后摘要或人物内心设定|

同一GPT上下文不会因换资料包真正遗忘大纲。在同一对话继续审阅，模式必须为`same_context_approximation`。只有确实另开独立输入环境、只提供读者包时才能写`isolated_input`，仍不叫真实读者测试；工具不能证明上下文已经隔离。

读者包超过预算时，用`--history-from/--history-to`分批读取旧章，保留范围；本包遗漏的章节不能宣布读过。默认报告中的coverage是来源绑定与阅读声明，不是程序看到模型实际阅读的证据。读者回顾也可能概括失真，疑点回查原文。

三个视角生成资料后都重新比较最初载入的完整state，不仅比较revision；reader还核对当前候选文件没有在生成途中改变。变化时停止输出，重新读取。`context --out`不能指向作品目录，也不能与`--text`是同一路径，避免将资料包写回草稿。

## 二、每天的最小顺序

1. 恢复当前状态、候选和返修次数。实际读必要来源与到期回看范围。
2. 准备本章任务书：自然语言写清目标、处境、主动选择、代价、硬边界、主要读者体验。长章先安排有作用的场景与汉字预算，合计符合本书章长。
3. 非首章用`history-search`查全书摘要和推进，换人物别名、办法、关系等词补查；必要时用`--before`专查最近三章之外的旧桥段。关键词未命中不是没有重复。
4. `brief-check`登记任务书，`context --profile writer`生成干净写作资料，写完整初稿后candidate。场景预算不是硬切字数，不为达标灌水。
5. 先只看正文反推实际场景、选择和变化，再对照任务书。不要从章纲复制“关系破裂”“局势逆转”作为实际结果。
6. 按reader资料检查理解缺口、信息负担和承诺兑现。对立方、对白、重要事件余波同时做专项判断，无适用场景则解释原因。
7. 填原有八项检查与新增`narrative_review`；有证据的问题局部repair，最多三轮。改正文后重新核对记录、证据、读者回顾与报告，不能复用旧版本。
8. 到期全文回看前置；release-check通过后adopt，正文、事实记录和审查依据一起冻结。提交GitHub并回读。发布另凭真实依据登记。

任务书是准备资料，不是新小说事实。登记或调整任务书不改变正式revision、候选任务和返修次数；新任务书哈希会让已有发布前报告失效。设定或路线版本变化也必须重新核对任务书。不要用重做任务书重开候选。

## 三、工具示例

所有路径和章号取真实状态，由GPT填写JSON。示例文件置于作品目录外；生成pending模板不代表任务完成。

```bash
python3 tools/novel_state.py --root book context --profile author --query "人物 办法 物品" --out drafts/作者资料.md
python3 tools/novel_state.py --root book brief-request --out drafts/本章任务书.json
# 实际读来源后填写decision=ready、writer_brief、hard_boundaries、reader_promise、scene_plan、history_queries
python3 tools/novel_state.py --root book history-search --query "借据 逼退 控制解释权" --limit 5
python3 tools/novel_state.py --root book brief-check --file drafts/本章任务书.json
python3 tools/novel_state.py --root book context --profile writer --out drafts/写作资料.md
# 起草完整正文，登记candidate，准备真实章后记录；随后生成限信息资料
python3 tools/novel_state.py --root book context --profile reader --text drafts/CH001.txt --out drafts/读者资料.md
python3 tools/novel_state.py --root book release-request --text drafts/CH001.txt --record drafts/CH001记录.json --out drafts/CH001检查.json
# 实际审阅填写，不批量自动置pass
python3 tools/novel_state.py --root book release-check --text drafts/CH001.txt --record drafts/CH001记录.json --report drafts/CH001检查.json
python3 tools/novel_state.py --root book adopt --text drafts/CH001.txt --record drafts/CH001记录.json
```

`context --profile author`保留旧接口。其必要资料太大时，直接分批读取state指向的不可变输入文件和历史正文，记录路径、哈希及已读范围，再提取任务书；不能把只看目录算读完。writer/reader资料也不会静默截断。reader分批示例：`--history-from 1 --history-to 5`，其中数字只作示例。

历史检索的`indexed_records`是全书索引条数，`scanned_records`是本次实际参与查询的范围；设置`--before`后不会把排除章节算成已查。查询、任务书和审查报告中的检索词都须包含实际文字或数字，纯标点不能当作检索完成。

## 四、发布前新增字段

`release-request`按真实候选动态生成，不由作者手填固定版本号。

|字段|实际要做的判断|程序能检查什么|
|---|---|---|
|writing_brief_sha256|写手是否依据正确任务书|当前任务书、书籍与设定路线绑定|
|actual_scenes、plan_comparison|本章真正发生了什么，哪些计划没做到或合理改变|字段、当前正文引文、版本；不能证明变化有分量|
|reader|正文是否讲清、信息是否超载、卖点是否实际兑现|资料来源版本、模式声明、具体结论与引文；不计算留存率|
|reader.issues|问题是否成立，如何处理|必须修或待核的问题未处理时阻断；偏好建议可以保留|
|character_causality|对手主动性、对白诉求与潜台词、行动后的反应和决定|适用性说明及引文；不要求每章都有反派、对白或高潮|
|history|全书同类桥段的办法、选择、代价有何差别|历史索引哈希、查询词、旧章与本章引文；不能自动判语义重复|
|reader_updates|只凭正文已能看到什么，哪些只是角色说法或疑点|observed／claim／uncertain与本章来源，不能继承作者未来计划|
|surface_findings|疑似制作句、控制字段和行内审稿标签是否进入正文|扫描结果不能漏掉；修正文后重查，确为故事内容须说明语境|

读者回顾不是第五种fact。客观事实、人物知情和猜测仍沿用原账本；这里只派生读者已看到的陈述及证据。不因人物说了就把内容标为客观真相。没有新增揭示时允许空updates，但说明本章体验与未变部分；该章日后进入较早前情时会退回原文，不用空列表代替已读内容。

全书历史索引覆盖已采用记录，仍不是全书正文阅读覆盖。没有相似桥段可比时允许空comparisons，但必须交代检索范围和局限；首章没有历史，查询词可以为空。最近三章原有比较仍保留。长篇到期回看照常实际读全文。

扫描只提示高特异性制作痕迹，不按P11、R03等一般编号一律删除，也不按词频或句长给AI概率。确有小说内程序或元叙事时可用`story_context`说明语境，不能用泛泛理由包庇真实制作语言。

## 五、修复优先级与负例

先核实事实与因果，再修人物选择、读者理解和兑现，再做对白或局部表达。三轮预算不因新模块增多而扩大；第一次完整稿之前的正常接续不计返修。

|负例|应如何处理|
|---|---|
|动机只在人物卡写了，正文没有线索|限信息审读标缺口，未冻结稿补必要行为或线索|
|章纲写“姐妹决裂”，正文只是互相复述账单|反向提纲如实记未产生对应变化，不靠改章后表格假装完成|
|换了道具，却又用同一种优势轻松逼退对手|回查全书同类桥段，调整未写路径与代价|
|反派无信息来源就知道主角秘密|必须修；不能靠“他早已料到”补万能解释|
|重大失败后立刻换场景，人物毫无反应|据题材补必要余波和下一决定，避免长段重复心理|
|章节没有对白|说明不适用，不能为通过对白项硬塞对话|
|本来是人物谎话，回顾却记成真相|改为claim或uncertain，保留原文；回查相应事实账|
|普通工程编号、书中人物正在谈写作|看语境，不把所有编号或“章”字当制作污染|

这些负例供GPT实际诊断，不是脚本已具备全部识别能力的声明。测试能证明跳步、失效版本、漏填证据等会被拦截，不能证明作品一定好看。
